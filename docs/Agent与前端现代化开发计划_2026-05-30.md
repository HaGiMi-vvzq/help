## 1. 文档目的

本文档用于承接当前校园 AI 互助匹配平台的下一阶段开发，重点解决两个方向：

1. Agent 目前已经具备会话、文件分析、需求草稿、确认发布、任务面板和匹配提醒的基础能力，但仍需要补齐“规划 - 执行 - 反馈 - 复盘”的闭环。
2. 当前前端能完成演示，但视觉层级、信息密度、交互反馈和页面质感仍偏 MVP，需要升级为更现代、更完整、更像真实产品的 Web 应用。

本文既是开发路线图，也是后续拆任务、验收和迭代的依据。

## 2. 当前判断

### 2.1 已经具备的基础

- 用户画像：支持自然语言简介、技能标签、院校资料、头像和资料持久化。
- 需求系统：支持求助、组队、技能交换三类需求，支持 AI 润色、AI 生成、需求模板、需求管理和选择候选人。
- 匹配系统：支持向量召回、LLM 精排、匹配理由、匹配进度、匹配结果对比表。
- 消息系统：支持按需求关联的站内消息、通知角标、已读状态。
- Agent 系统：支持 Agent 会话、文件上传分析、需求草稿生成、确认发布、任务面板、主动建议、记忆摘要和知识搜索后端能力。

### 2.2 主要短板

- Agent 任务目前更多是“计划展示”，还没有真正的任务执行器。
- Agent 的主动能力还弱，缺少定时跟进、状态追踪、失败重试和下一步建议。
- Agent 后端已有部分能力没有充分接入前端，例如知识搜索、私信起草、完整任务状态流。
- 前端页面能用，但视觉语言偏朴素，缺少统一设计系统、现代化布局、细腻状态和高质量空状态。
- 用户完成一个目标时仍需要在多个页面来回跳，缺少“工作台式”的连续体验。

## 3. 产品方向

下一阶段建议把平台从“AI 匹配演示工具”升级为：

> 面向校园协作的 AI 互助工作台。用户不仅能发布需求和找人，还能让 Agent 帮他理解文件、生成需求、比较候选人、起草消息、跟进进度、复盘合作质量。

这个方向有三个核心体验：

- **更聪明**：Agent 能主动规划、执行和提醒。
- **更可信**：匹配理由、任务状态、权限、隐私和反馈闭环清晰可见。
- **更好看也更好用**：页面像成熟产品，而不是比赛 demo 拼装页。

## 4. Agent 开发计划

### 阶段 A：Agent 稳定性与闭环基础

目标：让 Agent 的每个动作都有状态、有结果、有错误处理。

任务：

- 建立统一任务生命周期：`pending`、`running`、`waiting_user`、`done`、`failed`、`cancelled`。
- 为 `AgentTask` 补充任务类型、输入、输出、错误码、重试次数和关联对象，例如 `need_id`、`match_id`、`file_id`。
- 规划任务后不只写入数据库，还要进入执行队列。
- 前端任务面板展示任务时间线、失败原因、重试按钮和关联跳转。
- 为 Agent 关键接口补充更完整的回归测试。

验收标准：

- 用户输入 `/plan 帮我发布比赛组队需求` 后，右侧任务不只是显示计划，而是能看到每步执行状态。
- 某一步失败时，用户能看到失败原因，并能重试或改写要求。
- 刷新页面后任务状态不丢失。

### 阶段 B：Agent 任务执行器

目标：把 PlannerAgent 生成的计划变成可执行工作流。

建议实现一个轻量 `AgentTaskExecutor`：

- 根据 `assigned_agent` 或 `task_type` 分发到具体执行器。
- 支持内置执行器：文件分析、需求草稿、发布需求、运行匹配、生成私信、查询知识、生成总结。
- 支持父子任务：父任务汇总子任务状态。
- 支持后台执行：短任务同步执行，长任务后台执行。

优先实现的任务类型：

| 任务类型 | 说明 |
|---|---|
| `analyze_file` | 分析上传文件，提取主题、技能、截止日期和潜在需求 |
| `draft_need` | 根据文件或聊天内容生成需求草稿 |
| `publish_need` | 用户确认后发布需求 |
| `run_matching` | 触发匹配并监听结果 |
| `compare_matches` | 总结候选人优劣和适配建议 |
| `draft_message` | 为某个候选人起草联系消息 |
| `follow_up` | 对开放需求、未读消息、未选择候选人做提醒 |

验收标准：

- Agent 任务可以自动从一个步骤推进到下一个步骤。
- 任务失败不会静默消失。
- 每个执行器都能独立测试。

### 阶段 C：主动 Agent

目标：让 Agent 不只是被动聊天，而是能根据用户状态提出有用建议。

可实现能力：

- 开放需求超过一定时间未选择候选人，Agent 主动提示“是否帮你调整需求描述或扩大匹配范围”。
- 匹配结果出来后，Agent 主动给出候选人摘要和推荐排序。
- 用户联系候选人后，Agent 提醒后续跟进。
- 需求关闭后，Agent 询问是否记录合作反馈，用于优化后续匹配。

验收标准：

- 主动建议不只是固定文案，而是绑定具体需求、候选人或消息。
- 点击建议可以直接执行动作或跳到对应页面。
- 用户可以忽略、关闭或延后建议。

### 阶段 D：知识与记忆

目标：让 Agent 能长期理解用户和项目材料。

任务：

- 前端接入知识搜索 UI：搜索历史文件、分析结果、过往需求和匹配经验。
- 增加“文件库”：展示上传过的文件、解析摘要、可生成的需求。
- 增加“Agent 记忆面板”：展示系统记住了什么，允许用户删除或修正。
- 将成功匹配、用户选择、评分反馈沉淀为长期偏好。

验收标准：

- 用户能问“我之前上传的比赛通知里有哪些适合发布的需求？”
- 用户能看见并管理 Agent 记忆。
- Agent 能在新需求生成时引用历史偏好。

### 阶段 E：多轮智能追问链

目标：让 Agent 在需求不完整时主动追问，而不是一次性乱生成。

追问维度：

- 需求目标：想找人帮忙、组队、交换技能，还是咨询建议。
- 时间约束：截止日期、预计投入时长。
- 人员要求：人数、技能、年级、学院、线上/线下。
- 输出要求：最终交付物、比赛报名、课程作业、项目 demo。
- 风险点：隐私、能力要求过高、描述太模糊。

验收标准：

- 当用户只说“帮我找人做项目”时，Agent 会先追问关键信息。
- 当信息足够时，Agent 明确提示“可以生成需求草稿了”。

## 5. 前端现代化计划

### 5.1 设计目标

前端不应只追求“炫”，而要呈现一种现代校园协作产品的质感：

- 清晰的信息层级。
- 更强的工作台感。
- 更好的卡片、列表、表格和聊天体验。
- 更自然的 AI 状态反馈。
- 移动端和桌面端都能顺畅使用。

### 5.2 视觉方向

建议采用“轻量 SaaS + 校园协作”的设计语言：

- 主色：稳定的蓝色或青色，用于行动按钮和关键状态。
- 辅色：绿色表示匹配成功，橙色表示待处理，红色表示风险。
- 背景：浅灰白工作台背景，减少大面积纯白。
- 卡片：用于需求、候选人、任务、通知等重复项，圆角控制在 6-8px。
- 图标：统一使用 Element Plus Icons 或 lucide 风格图标，不再用乱码字符或 emoji 作为核心按钮。
- 字体层级：页面标题、区块标题、正文、辅助信息要有固定字号规则。

### 5.3 页面级改造

#### 应用外壳 AppLayout

- 左侧导航现代化：图标 + 文本，当前路由高亮。
- 顶部栏增加全局搜索、通知、用户菜单。
- 右下角 debug 面板仅开发模式显示。
- 移动端改为底部导航或抽屉导航。

#### 登录页

- 从普通表单升级为带产品识别的登录/注册页。
- 增加平台一句话定位和示例账号快捷填充。
- 注册流程可以引导用户填写第一版技能画像。

#### 画像页

- 做成分步式资料完善体验。
- 技能标签支持分组、推荐、置信度和手动调整。
- 增加“画像预览”：系统如何理解我、会如何匹配我。

#### 需求广场

- 增加筛选栏：类型、技能标签、学院、发布时间、状态。
- 需求卡片强化：发布者、标签、匹配热度、截止时间、状态。
- 增加列表/卡片视图切换。
- 增加搜索与排序。

#### 发布需求页

- 改为左右结构：左侧编辑，右侧 AI 建议和预览。
- 模板库做成可浏览的模板面板。
- AI 润色、AI 生成、标签提取、发布前检查集中在一个“AI 助手栏”。
- 发布前给出质量评分：标题是否清楚、技能是否明确、截止时间是否缺失。

#### 匹配结果页

- 顶部展示匹配概览：候选人数、平均匹配度、推荐首选、匹配耗时。
- 候选人卡片更精致：头像、技能、学院、匹配理由、风险提示、联系按钮。
- 对比表升级：支持固定候选人、按维度排序、隐藏低权重维度。
- 增加“让 Agent 帮我选择”按钮。

#### 消息页

- 对话列表更像现代聊天产品：头像、需求标题、未读角标、最后消息。
- 聊天窗口支持需求上下文卡片。
- 增加 AI 起草回复入口。
- 后续可以升级为实时消息或轮询刷新。

#### Agent 工作台

Agent 页应从“三栏聊天 demo”升级为真正的工作台：

- 左侧：会话和文件库。
- 中间：聊天与行动卡片。
- 右侧：任务时间线、主动建议、知识搜索。
- 支持行动卡片：需求草稿卡、候选人对比卡、私信草稿卡、文件摘要卡。
- 支持流式输出、任务进度、重试和取消。

### 5.4 交互与状态

需要统一补齐：

- 加载骨架屏。
- 空状态插画或高质量空状态文案。
- 错误状态和重试按钮。
- 成功反馈和下一步建议。
- 表单校验提示。
- 页面切换和卡片 hover 的轻量动效。
- 长任务进度提示。

### 5.5 前端工程整理

建议逐步建立：

- `components/common/`：通用按钮、状态标签、页面标题、空状态、加载状态。
- `components/agent/`：Agent 消息、任务、草稿、建议、文件卡片。
- `components/needs/`：需求卡、需求筛选、需求表单、模板面板。
- `components/match/`：候选人卡、对比表、匹配解释。
- `composables/`：通用请求状态、确认弹窗、响应式布局。
- 统一设计变量：颜色、间距、阴影、圆角、字体大小。

## 6. 项目功能扩展池

### 6.1 近期适合实现

这些功能能直接增强演示效果，开发成本也相对可控。

- **Agent 私信起草入口**：在匹配结果页和消息页接入后端 `draft-message`。
- **知识搜索面板**：让用户搜索历史文件、需求和 Agent 分析结果。
- **需求质量检查**：发布前检查标题、描述、技能、截止日期是否完整。
- **候选人收藏/置顶**：便于比较多个匹配对象。
- **匹配结果解释增强**：拆成技能匹配、时间匹配、经验匹配、潜在风险。
- **通知中心**：统一展示匹配完成、消息、Agent 建议、任务完成。
- **端到端测试**：覆盖注册、发布需求、匹配、联系、Agent 上传发布链路。

### 6.2 中期功能

- **团队组建模式**：一个需求可匹配多人，并显示团队技能覆盖度。
- **日程与可用时间**：用户填写空闲时间，匹配时考虑时间兼容性。
- **合作反馈闭环**：需求完成后互评，影响后续推荐权重。
- **技能图谱**：把技能标签组织成层级关系，例如前端、后端、数据、算法、设计。
- **智能需求订阅**：用户订阅感兴趣技能或比赛类型，有新需求时提醒。
- **多轮问答式发布需求**：用户不用填表，由 Agent 问完后生成。
- **推荐理由可视化**：用雷达图或维度条展示匹配结构。
- **文件多模态能力**：支持图片、扫描 PDF、海报 OCR。

### 6.3 长期功能

- **实时聊天**：WebSocket 或 SSE 支持消息实时到达。
- **小程序端**：校园场景更适合移动端触达。
- **组织/社群空间**：学院、课程、比赛、社团可以有专属空间。
- **管理员后台**：用户管理、内容审核、举报处理、数据看板。
- **推荐算法评估台**：记录召回、精排、点击、联系、完成率，用于优化匹配。
- **跨场景扩展**：从校园互助扩展到兴趣社群、开源协作、职场内推和项目组队。

## 8. 验收标准

下一阶段完成后，应该能演示以下完整故事：

1. 用户登录后进入一个现代化工作台。
2. 用户上传比赛通知 PDF 或 docx。
3. Agent 自动分析文件，生成需求草稿。
4. 用户确认发布。
5. 系统运行匹配，页面显示进度。
6. 匹配结果页以现代化候选人卡片展示推荐对象。
7. Agent 总结候选人差异，并建议优先联系谁。
8. 用户点击“起草私信”，Agent 生成自然的联系消息。
9. 用户发出消息。
10. 后续 Agent 在需求未关闭或候选人未回复时主动提醒。

## 9. 风险与注意事项

- 不要只做视觉皮肤。前端现代化必须同时改善信息结构和操作路径。
- Agent 不要假装自动化。凡是还没有执行器支撑的动作，都要清楚标注为建议或草稿。
- 长任务必须有进度、错误、重试和刷新恢复。
- AI 生成内容必须允许用户确认，不能直接替用户对外发布或发消息。
- 权限和隐私继续保持高优先级，尤其是文件、消息、匹配结果和用户画像。
- 不要一次性重写所有页面。应先建立设计系统，再逐页替换。
