# 校园 AI 互助撮合平台路演稿

适用场景：人工智能学院首届校园黑客松挑战赛路演  
时间安排：3 分钟汇报 + 2 分钟 Demo 演示  
目标：围绕评分标准突出真实需求、AI 赋能、产品闭环、落地可行性与现场表现  
说明：主稿按正常语速约 3 分钟；带技术细节的句子可以根据现场时间略讲或展开。

---

## 一、3 分钟汇报稿

各位评委老师好，我们的项目是 **校园 AI 互助撮合平台**。

我们关注的是一个非常真实的校园场景：同学们经常想参加比赛、做项目、补技能、找队友，但信息分散在群聊、朋友圈和熟人推荐里。发布需求的人很难找到合适的人，想参与的人也不知道哪里有适合自己的机会。所以我们做了一个 AI 平台，让需求发布、智能匹配、主动申请和后续沟通形成闭环。

我们的目标用户有两类：一类是发布方，比如想参加黑客松、蓝桥杯、课程项目的同学；另一类是参与方，比如有设计、前端、算法、文案能力，想找到合适项目加入的同学。平台的校园价值在于降低协作门槛，让“我需要帮助”和“我能提供帮助”更快连接起来。

在产品实现上，前端使用 **Vue 3、Vite、TypeScript、Element Plus、Pinia 和 Axios**，负责登录、需求广场、匹配结果、站内消息和 Agent 工作台等交互页面；后端使用 **FastAPI、异步 SQLAlchemy、SQLite、JWT 登录鉴权**，提供需求、用户、匹配、申请、消息和设置接口。这样既能快速开发，也能在路演现场本地稳定运行。

在 AI 技术上，我们不是简单加一个聊天框，而是把 AI 放进完整业务流程里。生成类任务调用 **DeepSeek 大模型 API**，完成需求理解、追问、需求草稿生成、申请文案和私信起草；匹配类任务使用本地打包的 **Qwen3-Embedding-0.6B** 把需求和用户画像转成语义向量，再用 **Qwen3-Reranker-0.6B** 对候选人精排，兼顾语义相似度和能力互补。为了保证演示稳定，我们还做了 API Key 检测和网络自动切换，默认网络不通时会尝试本地代理路径。

Agent 层面，我们做了三个封装。第一是 **Skill 封装**：把标签提取、向量生成、匹配召回、文件读取、任务规划、上下文总结、语义路由等能力都封成独立 Skill，并通过 `SkillRegistry` 统一注册和调用；第二是 **Prompt 提示词体系**：用 `PromptRegistry` 管理不同场景的 system prompt、user prompt 和 JSON 输出约束，比如意图识别、需求润色、匹配理由、私信起草都有独立模板；第三是 **Hooks 事件机制**：用轻量 `EventBus` 在用户注册、需求发布、匹配完成、文件处理、消息发送等节点触发后续动作，让业务流程可以自动衔接。

具体到对话体验，我们加入了 **语义路由和多技能编排**：系统会先判断用户是在“发布新需求”、“寻找已有需求”、“查看匹配”、“上传文件”还是“普通咨询”，再进入对应 Skill 和 Prompt。比如用户说“我会前端，想找个项目加入”，Agent 会走反向推荐；用户说“帮我发布一个黑客松组队需求”，Agent 会追问信息并生成草稿，避免把不同意图混在一起。

产品完整性方面，我们已经实现了登录、用户画像、需求发布、需求广场、我的需求、智能匹配、候选人比较、主动申请、申请审核、站内消息、消息通知弹窗和 Agent 工作台。发布方可以通过 Agent 描述想法，AI 追问关键信息并生成需求草稿，确认后发布，再查看候选人并联系对方。参与方可以让 Agent 推荐适合自己的现有需求，并一键起草申请消息。也就是说，这不是一个单点功能，而是一个可运行、可演示的双边协作撮合系统。

创新性上，我们的亮点有三个。第一，AI 不只生成文本，而是参与需求理解、匹配、推荐和沟通。第二，平台支持双边撮合，既能“发布需求找人”，也能“根据个人能力找需求”。第三，我们采用低成本落地方案：FastAPI、Vue、SQLite、本地 Qwen 模型，加上可配置的大模型 API Key，方便学校、学院或社团快速部署和二次孵化。

最后，我们希望这个项目不仅服务比赛展示，也能成为校园项目协作、赛事组队、课程互助和技能交换的基础平台。接下来我会用 2 分钟演示完整闭环。

## 二、2 分钟 Demo 演示口播

第一步，我用演示账号 `alice` 登录。这里可以看到系统已经内置了演示账号和校园协作数据。技术上这里走的是后端 JWT 登录鉴权，前端用 Pinia 保存登录状态，后续接口自动携带 token。

现在进入 **智能助手**。我告诉 Agent：我想参加一个黑客松，需要找前端、设计或算法方向的队友。可以看到 Agent 不是直接粗暴发布，而是会追问项目方向、技能需求和人数模式，然后生成结构化需求草稿。这里背后先由语义路由 Skill 判断用户意图，再通过专门的需求生成 Prompt 调用大模型，所以它不是固定问答，而是按任务动态选择能力。

接下来我点击确认发布。需求发布后，系统会进入匹配流程。后端会把需求标签和描述保存到 SQLite，同时调用本地 Qwen3 Embedding 生成需求向量，再和用户画像向量做召回。发布成功后，后台会启动匹配任务；匹配完成、文件处理、需求创建等节点会通过 Hooks 事件记录状态并推动后续通知。

现在进入匹配结果页。这里可以看到候选人的技能、匹配理由和对比信息。候选人排序不是简单关键词匹配，而是先用向量相似度召回，再用 Qwen3 Reranker 做交叉编码器精排，最后结合大模型生成可读的推荐理由。发布方可以比较候选人，并选择合适的人。

选择后，我可以让 AI 起草私信，系统会结合当前需求、候选人技能和匹配理由生成更自然的沟通文案。然后跳转到站内消息页，说明匹配后的沟通链路已经闭环。消息通知弹窗会从后端未读消息接口拉取数据，用户点开后可以直接进入对应对话或需求。

接下来演示参与方视角。用户也可以不是发布需求，而是告诉 Agent：“我想找一个适合我参与的项目。”Agent 会根据个人画像和已有需求反向推荐机会。进入需求详情后，参与方可以让 AI 起草申请消息，一键申请加入。发布方收到申请后可以接受或拒绝，申请状态会同步更新，并通过站内消息提醒双方。

所以整个 Demo 展示的是：AI 辅助发布需求、AI 智能匹配候选人、参与方主动申请、双方进入消息沟通。它覆盖了真实校园协作中的完整路径，也对应了从前端交互、后端业务接口、数据库状态、AI 推理到消息通知的完整技术闭环。

## 五、技术细节速记表

| 展示位置 | 用到的技术 | 你可以怎么讲 |
| --- | --- | --- |
| 登录与页面框架 | Vue 3、Vite、TypeScript、Element Plus、Pinia、Axios | 前端是单页应用，负责把需求、匹配、消息和 Agent 流程串成可演示界面 |
| 后端接口 | FastAPI、异步 SQLAlchemy、SQLite、Pydantic、JWT | 后端提供用户、需求、匹配、申请、消息、设置等接口，本地 SQLite 方便路演运行 |
| Skill 能力封装 | BaseSkill、SkillRegistry、TagSkill、EmbedSkill、MatchSkill、FileReaderSkill、SemanticRouterSkill | 每个 AI 能力都是可注册、可复用、可组合的 Skill，不是散落在业务代码里的临时函数 |
| Prompt 提示词体系 | PromptRegistry、PromptTemplate、system prompt、user prompt、few-shot、JSON 输出约束 | 不同场景用不同 Prompt 模板，保证需求生成、意图识别、推荐理由和私信起草更稳定 |
| Agent 判断意图 | SemanticRouterSkill、DeepSeek JSON 输出、启发式 fallback | 先判断用户是发布需求、找需求、看匹配还是上传文件，再进入对应技能 |
| 需求草稿与消息文案 | DeepSeek 大模型、Agent Planner、Need Creator、私信起草 Prompt | 大模型不是闲聊，而是生成结构化需求、申请理由和沟通文案 |
| 智能匹配召回 | Qwen3-Embedding-0.6B、sentence-transformers、向量相似度 | 把需求和用户画像变成语义向量，解决“词不一样但意思相近”的匹配问题 |
| 候选人精排 | Qwen3-Reranker-0.6B、CrossEncoder、匹配分数归一化 | 对候选人和需求做二次精排，比单纯关键词或单纯向量更稳 |
| 推荐理由 | DeepSeek 生成理由、技能标签、用户画像、匹配上下文 | 评委看到的不只是分数，还有为什么这个人适合当前需求 |
| 反向找需求 | 用户画像向量、已有需求向量、关键词相似度融合 | 参与方也能根据自己的能力找适合加入的项目，体现双边撮合 |
| 站内消息与通知 | 消息表、未读状态、通知接口、前端弹窗 | 匹配、申请、私信之后能继续沟通，形成产品闭环 |
| Hooks/事件机制 | EventBus、emit_background、user_registered、feedback_received、need_published、agent_match_completed、message_sent | 关键业务节点会触发事件，用于画像初始化、反馈反思、Agent 文件/需求/匹配状态记录和后续通知扩展 |
| 演示稳定性 | API Key 检测、DeepSeek 默认网络/本地代理自动切换、本地 Qwen 模型 | 远程模型可检测，本地模型已打包，网络不稳时也尽量不影响核心演示 |
