# 黑客松前端演示层升级设计文档

## 1. 背景

当前项目的业务闭环已经基本具备：Agent 上传/追问/出草稿、确认发布、匹配结果、私信起草都能工作。现阶段的主要短板不是功能缺失，而是演示层不够成熟，页面之间的视觉语言、信息层次和产品感仍然偏轻，容易在路演时给人“功能有了，但像开发态界面”的印象。

本轮目标是在不冒大风险的前提下，把前端从“可用”提升到“可演示、可讲故事、看起来像成品”。

## 2. 范围

### 2.1 本轮纳入范围

- 全局视觉 token 和页面骨架统一
- `AppLayout` 升级
- `AgentView` 升级
- `NeedPlazaView` 升级
- `MatchResultView` 风格并线和信息层次增强
- 路由级代码拆分，降低主包压力

### 2.2 本轮不纳入范围

- 重写后端接口或业务流程
- 引入新的 UI 框架
- 重做登录、消息、设置等非主舞台页面
- 动画驱动的复杂视觉效果
- 依赖浏览器自动化才能稳定维护的交互

## 3. 设计目标

### 3.1 主目标

1. 演示链路连续且清楚：进入系统 -> Agent -> 发布需求 -> 匹配结果 -> 私信联系
2. 全站观感统一，像一个完整产品，而不是若干页面拼接
3. AI 差异化集中体现在 Agent 工作台，而不是全站到处“AI 风格化”
4. 维持实现稳定性，不做高风险大重构

### 3.2 成功标准

- 首页、Agent、匹配结果三处核心舞台视觉层级明显提升
- 首屏内能看懂当前页面的主任务和下一步动作
- 评委看 10-20 秒能理解产品定位和主要流程
- 构建通过，核心自动化测试继续通过

## 4. 设计原则

### 4.1 风格原则

- 主体采用浅色专业基调
- 侧边导航、AI 状态块、关键摘要区使用深色强调
- 减少“营销页式夸张”，保留产品工作台质感
- 控制圆角、阴影和颜色数量，避免花哨

### 4.2 结构原则

- 页面优先服务任务，不用大段说明文字
- 信息布局以“概览 -> 当前操作 -> 深层细节”展开
- 每个主页面都要有一个明确的视觉中心
- 复用现有组件和数据流，不新造一套状态体系

### 4.3 风险控制原则

- 不改后端契约
- 不改高风险交互语义，只重排表现层
- 每改一层都能单独回归构建和页面逻辑

## 5. 总体视觉方案

### 5.1 视觉基调

- 页面背景：浅灰白
- 卡片背景：纯白或非常浅的分层白
- 导航与 AI 强调区：深蓝灰
- 品牌主色：冷调亮蓝
- 辅助语义色：成功绿、警示橙、错误红，低饱和使用

### 5.2 Token 调整方向

- 统一边框颜色和 hover 层级
- 缩减主色变体数量，避免发散
- 提升标题层级差异
- 让阴影更轻、更靠边界和层次，而不是靠悬浮感堆效果

### 5.3 页面宽度策略

- 主容器改为更稳定的内容宽度上限
- 工作台类页面允许更宽，但仍保留阅读边界
- 卡片和表格区使用固定网格与最小宽度，避免内容挤压变形

## 6. 信息架构

### 6.1 AppLayout 角色

`AppLayout` 负责建立“成熟产品”的第一印象，不负责讲复杂功能。

#### 布局结构

- 左侧：深色导航栏
- 顶部：浅色状态栏
- 内容区：统一背景和滚动容器

#### 导航表现

- 品牌区从简单文字升级为更完整的产品标识区
- 导航项加入更清晰的激活态和 hover 态
- 用户区、通知区、当前页标题的关系更明确

#### 预期效果

- 进入系统第一眼更像 SaaS 产品
- 无论跳到 Agent 还是需求页，视觉框架都一致

### 6.2 AgentView 角色

`AgentView` 是整场路演的 AI 主舞台，重点不是聊天，而是“Agent 正在代你推进任务”。

#### 三栏结构保留，但重新分工

- 左栏：会话与上下文入口
- 中栏：对话与系统产出
- 右栏：建议、记忆、知识、任务状态

#### 中栏重点升级

- 欢迎区从“空白聊天页”升级为可直接演示的行动面板
- 消息卡片统一成工作流输出格式
- 文件分析、需求草稿、计划、发布结果都使用更明确的结果卡样式
- 输入区强化“上传文件 / 发送目标 / 制定计划”三个动作

#### 右栏重点升级

- 主动建议改为更像下一步动作中心
- 知识搜索、文件库、记忆摘要做成同一视觉体系
- 任务时间线强化状态感，突出运行中、等待用户、失败可重试

#### 左栏重点升级

- 会话项强化更新时间和激活态
- 新建会话按钮更明显，但不喧宾夺主

#### 预期效果

- Agent 页不再像聊天窗口，而像 AI 运营台
- 用户能一眼看懂“现在进行到哪一步、下一步做什么”

### 6.3 NeedPlazaView 角色

`NeedPlazaView` 负责证明这不是单点 AI 工具，而是完整平台。

#### 页面结构

- 顶部概览区：页面标题 + 简短定位 + 主操作按钮
- 中部筛选区：类型筛选更像工具栏
- 主体内容区：需求卡片网格

#### 卡片改造

- 强化类型、状态、作者、时间的层次
- 标题更稳，描述更易扫读
- hover 时突出“可点进去看匹配结果”的可操作性
- 适度增加信息密度，但保持卡片整洁

#### 可追加的小型概览

- 在页头加入简短统计，例如“开放需求数 / 组队需求数 / 今日新增”
- 统计只作为视觉补强，不引入新接口时可由现有列表粗算

#### 预期效果

- 需求广场更像真实业务首页
- 演示时能快速说明“平台上已有流动内容”

### 6.4 MatchResultView 角色

`MatchResultView` 负责建立结果可信度和决策效率。

#### 升级重点

- 顶部增加结果概览区，快速说明匹配人数、最高分、推荐建议
- 候选人卡片和对比表视觉并线
- 私信起草入口更自然地嵌入卡片和对比逻辑
- 关键推荐理由的可读性增强

#### 不做的事

- 不改已有核心业务逻辑
- 不重写候选人数据结构

#### 预期效果

- 页面更像“决策台”，不是“调试输出结果页”

## 7. 技术设计

### 7.1 样式层

- 继续基于现有 `global.css` 和各页面 scoped CSS
- 先统一全局 token，再局部重写关键页面
- 不引入 Tailwind、不切换设计系统

### 7.2 组件层

- 保持现有视图文件主导
- 可抽出少量高复用展示块，但不做大规模组件拆分
- 优先在既有文件内收敛结构和样式

### 7.3 路由层

- 将页面级组件改为懒加载
- 优先拆出 `AgentView`、`MatchResultView`、`NeedPlazaView` 等较重页面
- 目标是降低首页主包体积，改善演示时冷启动观感

## 8. 错误与降级

### 8.1 视觉降级

- 如果某块增强效果风险高，退回静态卡片，不影响业务逻辑
- 避免依赖复杂动画和异步视觉效果

### 8.2 数据降级

- 所有新增概览区都必须允许“无数据”状态
- 不允许因为统计或附加摘要失败而影响主流程

### 8.3 交互降级

- 移动端保留现有侧滑逻辑，不重新发明导航模式
- 行为入口尽量复用已有按钮和 store action

## 9. 测试与验收

### 9.1 必做验证

- `npm run build`
- `backend` 现有契约测试
- `backend` smoke test

### 9.2 手动回归链路

1. 进入需求广场
2. 打开 Agent
3. 上传文件或追问生成草稿
4. 确认发布
5. 跳转匹配结果
6. 起草私信并进入消息页

### 9.3 视觉验收

- 框架统一，无明显“旧页面风格残留”
- 文本不溢出、按钮不抖动、卡片不乱层
- 桌面端主演示路径优先稳定

## 10. 实施顺序

1. 全局 token 和 `AppLayout`
2. `AgentView`
3. `NeedPlazaView`
4. `MatchResultView`
5. 路由懒加载与构建回归

## 11. 风险与取舍

### 11.1 主要风险

- 页面重写过多导致样式回归
- 包拆分时引入路由或导入错误
- Agent 页局部结构变化影响既有交互

### 11.2 取舍策略

- 先保演示链路，不追求全站精修
- 先做层级和骨架，再做局部装饰
- 优先提升“像产品”的信号，不追求复杂视觉特效

## 12. 结论

本设计采用“浅色为主、深色强调”的稳态升级方案，以 `AppLayout + AgentView + NeedPlazaView + MatchResultView` 为主战场，目标是在不改变业务闭环的前提下，把系统提升为适合黑客松路演的产品级演示界面。

这不是一次全站推倒重来，而是一次围绕演示链路的高回报重构。
