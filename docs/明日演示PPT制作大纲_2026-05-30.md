# 校园 AI 互助撮合平台明日演示 PPT 制作大纲

> 用途：给负责做演示 PPT 的队友使用。目标是在 5-8 分钟内讲清楚“我们解决什么问题、怎么解决、现场能跑通什么、为什么有价值”。

## 1. PPT 总体叙事

建议把 PPT 讲成一个完整故事：

学生经常想参加比赛、做项目、找技术指导，但不知道该找谁、怎么描述需求、怎么开启沟通。我们的平台把“发布需求、AI 辅助整理、智能匹配、主动申请、站内沟通”串成闭环，让校园协作从“到处问人”变成“Agent 帮你找对人并推进合作”。

核心关键词：

- 校园协作
- AI 互助
- 双边撮合
- Agent 工作台
- 需求发布与反向推荐
- 匹配后沟通闭环

## 2. 推荐页数与结构

建议做 12 页左右，控制信息密度，避免堆功能列表。

### 第 1 页：封面

标题建议：

**校园 AI 互助撮合平台**

副标题建议：

让 Agent 帮学生发布需求、找到队友、推进合作。

画面建议：

- 放平台首页或 Agent 工作台截图。
- 视觉上突出“AI + 校园协作 + 撮合”。

讲述重点：

- 我们做的不是普通论坛，而是一个带 Agent 的校园协作工作台。

### 第 2 页：问题背景

标题建议：

**校园协作为什么难？**

内容建议：

- 想参加比赛、课程项目、大创、黑客松时，经常不知道谁合适。
- 需求描述不完整，别人看不懂，也不好判断是否加入。
- 找到人以后缺少统一沟通入口，状态容易断掉。
- 发布方和参与方的信息不对称：一个找不到人，一个找不到合适机会。

画面建议：

- 左侧放“学生需求场景”：算法比赛、黑客松、大创、技能求助。
- 右侧放痛点关键词云或流程断点图。

### 第 3 页：解决方案概览

标题建议：

**用 AI Agent 串起校园互助闭环**

内容建议：

平台提供四个核心能力：

- Agent 辅助整理需求：聊天、追问、文件分析、生成草稿。
- 智能匹配候选人：基于用户画像、技能、需求语义生成推荐。
- 双边申请机制：用户可以主动申请加入已有需求。
- 消息沟通闭环：匹配或申请后直接进入站内消息。

画面建议：

画一条流程：

`表达想法/上传文件 -> Agent 生成需求 -> 发布 -> 匹配/申请 -> 选人 -> 消息沟通`

### 第 4 页：系统角色与使用场景

标题建议：

**两个视角：发布方和参与方**

内容建议：

发布方：

- 发布比赛组队、项目协作、技术求助等需求。
- 查看候选人匹配结果。
- 选择候选人并联系。

参与方：

- 浏览需求广场。
- 让 Agent 推荐适合自己的已有需求。
- 主动申请加入。
- 查看申请状态和被选中的需求。

画面建议：

- 用两列卡片展示“发布方视角”和“参与方视角”。

### 第 5 页：核心亮点 1 - Agent 工作台

标题建议：

**Agent 不只聊天，还能帮你把想法变成可发布需求**

内容建议：

- 支持自然语言对话。
- 信息不完整时会追问，例如需求类型、标题、人数。
- 支持上传比赛通知或项目文件，自动提取主题、技能、截止时间。
- 可生成一条或多条需求草稿，并由用户选择后发布。

截图建议：

- Agent 工作台页面。
- 需求草稿卡片。
- 文件分析结果卡片。

讲述重点：

- 强调“用户最后确认”，避免让评委误以为系统会无控制地自动发布。

### 第 6 页：核心亮点 2 - 智能匹配与候选人比较

标题建议：

**从发布需求到找到合适队友**

内容建议：

- 发布需求后生成匹配结果。
- 展示候选人的技能、简介、匹配理由。
- 支持候选人对比。
- 支持起草联系消息。

截图建议：

- 匹配结果页。
- 候选人卡片。
- 候选人对比表。

讲述重点：

- 不只是“列人名”，而是给出为什么适合。

### 第 7 页：核心亮点 3 - 反向发现已有需求

标题建议：

**不想发布？Agent 也能帮你找现有机会**

内容建议：

- 用户说“我想打算法比赛，帮我找现有需求”。
- Agent 应识别为“发现已有需求”，不是发布新需求。
- 系统推荐适合参与的需求。
- 用户可查看详情并申请加入。

截图建议：

- Agent 推荐已有需求的对话截图。
- 推荐需求卡片。
- 需求详情页申请入口。

讲述重点：

- 这是双边撮合的关键：平台同时服务“找人”和“找机会”。

### 第 8 页：核心亮点 4 - 申请、选择与状态闭环

标题建议：

**申请状态不再断链：待处理、已通过、未通过都可追踪**

内容建议：

- 参与方提交申请后，可在“我的申请”查看状态。
- 发布方可接受或拒绝申请。
- 单人需求完成配对后，未选中的待处理申请会自动结束为未通过。
- 被选中用户可在“我的需求”看到自己被选中的需求，并继续沟通。

截图建议：

- 我的申请页面。
- 我的需求页面，展示“我发布的需求”和“我被选中的需求”两类卡片。
- 消息页。

讲述重点：

- 最近已重点修复状态流转，演示时要体现平台闭环而不是停在“待处理”。

### 第 9 页：系统架构

标题建议：

**前后端与 AI 服务架构**

内容建议：

推荐画简化架构图：

- 前端：Vue 3 + Element Plus。
- 后端：FastAPI。
- 数据层：SQLite，本地演示数据库。
- AI 能力：模型 API、Agent Planner、文件分析、需求生成、消息起草。
- 核心业务服务：需求服务、匹配服务、申请服务、消息服务、设置服务。

画面建议：

用 4 层结构：

`用户界面 -> API 服务 -> 业务服务/Agent -> 数据库/模型服务`

### 第 10 页：演示主线

标题建议：

**现场演示路线**

建议演示顺序：

1. 登录 `alice / 123456`。
2. 打开智能助手。
3. 输入或上传黑客松/比赛材料。
4. Agent 生成需求草稿。
5. 选择草稿并确认发布。
6. 进入匹配结果页，查看候选人。
7. 选择候选人或起草私信。
8. 切换到参与方账号查看申请/消息状态。

画面建议：

- 用时间线展示，不要把所有页面截图都堆上。

讲述重点：

- PPT 只做铺垫，真正价值由现场操作证明。

### 第 11 页：稳定性与测试保障

标题建议：

**赛前我们重点保障了演示稳定性**

内容建议：

- 登录、发布需求、Agent 草稿、文件上传、匹配、申请、消息等主链路已做回归测试。
- 修复了需求删除 500、Agent 把“找现有需求”误判为“发布需求”、多草稿不可选择、申请状态不流转等演示风险点。
- 后端健康检查、前端构建、后端测试作为赛前检查项。

画面建议：

- 放测试清单截图或状态勾选图。

### 第 12 页：总结与未来扩展

标题建议：

**从撮合平台到校园 AI 协作助手**

当前已完成：

- Agent 辅助发布。
- 智能匹配。
- 双边申请。
- 消息沟通。
- 状态闭环。

未来可扩展：

- 更完整的 Agent 任务执行器。
- 长期记忆与个人偏好学习。
- WebSocket 实时协作。
- 小程序端。
- 合作反馈与匹配质量评估。

收束话术：

“我们希望这个平台最终成为校园里的 AI 协作入口：当学生想做一件事时，不只是发帖，而是有一个 Agent 帮他把事情讲清楚、找到合适的人，并推进到真正合作。”

- 候选人对比表。
- 我的申请页面。

## 4. 演示口径注意事项

- 不要说“平台已经完全自动执行所有任务”，更准确的说法是“当前是可演示的 Agent 工作台，已能辅助生成、发布、匹配和沟通，赛后可扩展为自动执行器”。
- 不要承诺大规模推荐算法效果已完成评估，当前重点是闭环与可解释匹配。
- 演示 API 设置时不要展示完整密钥，截图里应遮挡。
- 如果 AI 模型临时不可用，可以说明系统有 fallback，核心业务链路仍可继续。
- 演示前不要现场重置数据库，除非已经确认备份和默认数据可恢复。

## 6. 最终检查

交付 PPT 前逐项确认：

- 每页标题能单独讲清楚一个观点。
- 每页最多 3-5 个要点。
- 截图中文字清晰，不暴露 API Key。
- 演示主线和测试文档中的主线一致。
- 不把未完成的赛后规划讲成已完成能力。
