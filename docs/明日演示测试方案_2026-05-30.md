# 校园 AI 互助撮合平台明日演示测试方案

> 用途：给队友按步骤做赛前测试。目标是覆盖功能测试、逻辑测试、异常测试和演示风险点，确保明天演示链路顺、状态对、页面不报错。

## 1. 测试目标

本轮测试不是为了覆盖所有研发细节，而是为了保证明天演示不会在关键路径上卡住。

必须确认：

- 前后端服务可访问。
- 演示账号可登录。
- Agent 能完成需求草稿生成、选择和发布。
- 需求、匹配、申请、消息四条主链路能闭环。
- 状态流转符合用户直觉，不能出现“已配对但申请还待处理”。
- 异常操作不会直接 500 或让页面卡死。

## 2. 测试环境与账号

### 2.1 默认地址

- 前端：`http://127.0.0.1:5173`
- 后端：`http://127.0.0.1:8000`
- 后端健康检查：`http://127.0.0.1:8000/api/health`

### 2.2 演示账号

密码均为 `123456`。

- `alice`：推荐主视角，适合演示 Agent、匹配、消息主链。
- `bob`：候选合作者，适合演示申请、被拒绝、消息。
- `iris`：高质量候选人，适合演示被选中、继续沟通。
- `eve`：设计方向画像，适合演示不同技能画像。
- `test`：如本地已有该账号，可用于复测 ICPC 状态流转。

### 2.3 测试记录格式

每个场景测试后记录：

- 结果：通过 / 不通过 / 阻塞。
- 账号。
- 页面。
- 实际现象。
- 截图或报错。
- 是否影响明天演示。

## 3. 演示前 10 分钟冒烟检查

这一组测试必须在正式演示前再跑一遍。

### S0-1 后端健康检查

步骤：

1. 打开浏览器访问 `http://127.0.0.1:8000/api/health`。
2. 查看返回内容。

预期结果：

- 返回 `{"status":"ok"}`。

失败处理：

- 如果打不开，先重启后端。
- 如果端口被占用，结束旧的 8000 端口进程后重启。

### S0-2 前端可访问

步骤：

1. 打开 `http://127.0.0.1:5173/login`。
2. 页面刷新一次。
3. 打开浏览器控制台，观察是否有红色报错。

预期结果：

- 登录页正常显示。
- 没有影响页面加载的红色错误。

### S0-3 登录与导航

步骤：

1. 使用 `alice / 123456` 登录。
2. 依次点击左侧导航：需求广场、发布需求、我的需求、My Applications、智能助手、站内消息、个人中心、系统设置。

预期结果：

- 每个页面都能打开。
- 页面可以上下滚动。
- 不出现空白页、死循环跳转或权限异常。

## 4. 功能测试场景

### F1 登录与账号切换

目的：

确认演示账号可用，退出和切换账号不会串状态。

步骤：

1. 访问登录页。
2. 使用 `alice / 123456` 登录。
3. 确认进入需求广场或首页。
4. 退出登录。
5. 使用 `bob / 123456` 登录。
6. 确认页面显示为 bob 的登录态。

预期结果：

- 两个账号都能登录。
- 切换账号后，不应继续显示上一个账号的个人状态。

异常补测：

1. 使用 `alice / wrong-password` 登录。
2. 确认页面提示登录失败。
3. 页面不能崩溃，也不能进入系统。

### F2 系统设置 API Key 更新

目的：

确认通过设置页变更 API 后，平台相关 AI 功能仍可使用。

注意：

- 不要在截图、PPT 或群聊中暴露完整 API Key。
- 测试记录中最多写“已填入新 key”，不要写明文。

步骤：

1. 使用 `alice` 登录。
2. 打开“系统设置”。
3. 查看 API Key 输入框和服务状态。
4. 填入新的 API Key。
5. 点击保存。
6. 刷新页面，再进入系统设置。
7. 确认页面提示保存成功，且说明“变更立即生效”或状态正常。
8. 打开智能助手，输入：`帮我用一句话总结这个平台能做什么`。

预期结果：

- 保存操作成功，不出现 500。
- 刷新后设置页仍能正常打开。
- Agent 能返回结果；如果外部模型不可达，也应有 fallback 或错误提示，页面不能卡死。

### F3 手动发布需求

目的：

确认不依赖 Agent 时，基本需求发布功能可用。

步骤：

1. 使用 `alice` 登录。
2. 打开“发布需求”。
3. 选择类型：`组队`。
4. 标题填写：`TEST-演示前手动发布黑客松需求`。
5. 描述填写：`需要会 Vue、Python 或项目展示的同学一起完善黑客松路演。`
6. 选择单人或多人模式，建议先选 `多人`。
7. 提交发布。
8. 跳转或打开“需求广场”，查找刚发布的需求。

预期结果：

- 发布成功。
- 需求广场能看到该需求。
- 需求详情页信息完整。

清理建议：

- 测完后可在“我的需求”删除该测试需求，确认删除不报 500。

### F4 Agent 对话发布需求

目的：

确认 Agent 能通过追问整理需求草稿，并发布。

步骤：

1. 使用 `alice` 登录。
2. 打开“智能助手”。
3. 新建或进入一个 Agent 会话。
4. 输入：`我想参加校园黑客松，帮我发布一个找前端和演示队友的组队需求`。
5. 如果 Agent 追问需求类型，回答：`组队`。
6. 如果 Agent 追问标题，回答：`黑客松前端和路演队友`。
7. 如果 Agent 追问人数，回答：`多人`。
8. 等 Agent 生成需求草稿。
9. 点击确认发布。
10. 打开“我的需求”或需求广场，查看新需求。

预期结果：

- Agent 能生成草稿。
- 确认发布后只发布一次。
- 页面不出现重复需求。
- 我的需求中可看到该需求。

重点观察：

- 确认按钮连点时，不应发布多条重复需求。

### F5 Agent 查找已有需求，而不是发布需求

目的：

复测之前的关键问题：用户想“找现有需求”时，Agent 不能误判为“发布需求”。

步骤：

1. 使用 `bob` 登录。
2. 打开“智能助手”。
3. 输入：`我想打算法比赛，帮我看看有没有这方面的组队需求`。
4. 如果 Agent 要标题，继续输入：`帮我找现有的需求`。
5. 如果 Agent 问单人/多人，输入：`单人`。

预期结果：

- Agent 应推荐已有需求或引导查看已有需求。
- 不应直接生成“可发布需求草稿”并要求确认发布。
- 如果出现推荐卡片，应能打开需求详情或继续申请。

失败标准：

- 只要 Agent 把该场景再次导向“发布需求”，就记为不通过。

### F6 文件上传生成多条需求草稿并选择发布

目的：

确认上传文件后多条草稿可以选择，而不是只能一起发布或无法选择。

步骤：

1. 使用 `alice` 登录。
2. 打开“智能助手”。
3. 上传一份比赛通知或项目说明文件；如果没有文件，可用简单 `.txt` 文件，内容包含：
   `校园黑客松，需要 48 小时完成智慧校园应用，团队需要 AI 开发、前端开发、项目展示。`
4. 等待 Agent 分析。
5. 查看是否生成一条或多条需求草稿。
6. 如果生成多条草稿，点击其中一条草稿卡片。
7. 确认按钮文案应体现“发布选中的 N 条需求”。
8. 点击确认发布。

预期结果：

- 草稿卡片可点击选择。
- 只发布被选中的草稿。
- 未选中的草稿不会被误发布。
- 发布后页面状态清晰，不让用户误以为还要重复发布。

### F7 匹配结果与候选人沟通

目的：

确认发布方能查看匹配结果、选择候选人、起草消息并进入沟通。

步骤：

1. 使用 `alice` 登录。
2. 打开“我的需求”。
3. 找到一个已有需求或刚发布的需求。
4. 点击查看匹配结果。
5. 查看候选人卡片和对比表。
6. 点击某个候选人的“起草私信”。
7. 查看 Agent 生成的私信内容。
8. 点击联系或进入消息页。
9. 发送一条消息：`你好，我们可以今晚一起确认分工吗？`

预期结果：

- 匹配页正常加载。
- 候选人卡片不串人，给 bob 起草的消息不能显示成 iris 的状态。
- 消息页能打开并发送成功。

### F8 主动申请加入需求

目的：

确认参与方可以主动申请已有需求，发布方可以看到申请。

步骤：

1. 使用 `bob` 登录。
2. 打开需求广场。
3. 找到一个 `alice` 发布的开放需求。
4. 进入需求详情。
5. 点击申请加入。
6. 填写申请消息：`我会 Vue 和数据可视化，希望加入这个项目。`
7. 提交申请。
8. 打开“My Applications”。
9. 查看该申请状态。
10. 退出，使用 `alice` 登录。
11. 打开“我的需求”或需求详情中的申请入口。
12. 查看 bob 的申请。

预期结果：

- bob 提交后状态为 `待处理`。
- alice 能看到 bob 的申请。
- 页面不重复提交同一申请。

### F9 发布方接受申请

目的：

确认接受申请后，申请方状态更新为已通过，并能进入沟通。

步骤：

1. 继续 F8 的数据。
2. 使用 `alice` 登录。
3. 找到 bob 对该需求的申请。
4. 点击接受。
5. 使用 `bob` 登录。
6. 打开“My Applications”。
7. 查看刚才申请的状态。
8. 打开消息页，查看是否有来自 alice 的通知或可继续沟通。

预期结果：

- bob 的申请状态变为 `已通过` 或 `accepted`。
- bob 不应继续看到 `待处理`。
- 消息页可以继续沟通。

### F10 单人需求完成配对后，其他申请自动结束

目的：

复测最近修复的状态流转问题：单人需求已选中一个人后，其他待处理申请不能继续显示待处理。

步骤：

1. 使用 `alice` 登录。
2. 发布一个单人需求，标题：`TEST-单人算法比赛搭子`。
3. 使用 `bob` 登录，申请该需求。
4. 使用 `iris` 登录，也申请该需求。
5. 使用 `alice` 登录，进入该需求的申请或匹配页面。
6. 选择 `bob` 作为最终人选，或接受 bob 的申请。
7. 使用 `bob` 登录，打开“My Applications”。
8. 使用 `iris` 登录，打开“My Applications”。

预期结果：

- bob 状态为 `已通过` 或 `accepted`。
- iris 状态为 `未通过`、`已拒绝` 或 `rejected`。
- iris 不能继续显示 `待处理`。
- 需求状态应体现已匹配或已结束。

失败标准：

- 只要未选中的申请仍显示待处理，就记为不通过。

### F11 选择推荐候选人后，被选中人能看到事件

目的：

确认“发布方选择候选人”不是单向状态，候选人也能看到并继续互动。

步骤：

1. 使用 `alice` 登录。
2. 打开一个需求的匹配结果页。
3. 选择 `iris` 作为候选人。
4. 退出，使用 `iris` 登录。
5. 打开“我的需求”。
6. 查看“我被选中的需求”区域。
7. 找到 alice 的需求。
8. 点击“去沟通”或“查看需求”。

预期结果：

- iris 能看到自己被选中的需求。
- 可以跳到详情页或消息页。
- 不需要 iris 猜测去哪里处理这个事件。

### F12 我的需求页面卡片展示

目的：

确认“我发布的需求”和“我被选中的需求”两类卡片都可见。

步骤：

1. 使用 `alice` 登录。
2. 打开“我的需求”。
3. 查看“我发布的需求”。
4. 使用 `iris` 登录。
5. 打开“我的需求”。
6. 查看“我被选中的需求”。

预期结果：

- alice 能看到自己发布的需求。
- iris 能看到自己被选中的需求。
- 卡片按钮可点击，跳转正常。

### F13 需求删除不报 500

目的：

复测曾经出现过的删除已有需求 500 问题。

步骤：

1. 使用 `alice` 登录。
2. 发布一个测试需求：`TEST-删除验证需求`。
3. 使用 `bob` 申请该需求。
4. 使用 `alice` 打开“我的需求”。
5. 删除这个测试需求。
6. 刷新页面。
7. 使用 `bob` 打开“My Applications”。

预期结果：

- 删除成功，不出现 `Request failed with status code 500`。
- 需求不再出现在 alice 的我的需求中。
- bob 的申请列表不应因该需求被删除而导致页面报错。

### F14 消息页刷新与路由切换

目的：

确认从不同入口进入消息页时，消息对象和 needId 不串。

步骤：

1. 使用 `alice` 登录。
2. 从匹配结果页联系 bob。
3. 发送一条消息。
4. 返回匹配结果页，再联系 iris。
5. 发送另一条消息。
6. 在消息页切换 bob 和 iris 的对话。
7. 刷新当前消息页。

预期结果：

- bob 和 iris 的对话不混在一起。
- 刷新后仍显示正确对话。
- needId 上下文不丢失。

## 5. 逻辑测试场景

### L1 权限隔离

目的：

确认用户不能查看或操作不属于自己的敏感页面。

步骤：

1. 使用 `alice` 打开某个自己发布需求的匹配结果页，记录 URL。
2. 退出，使用 `bob` 登录。
3. 粘贴刚才的匹配结果页 URL。

预期结果：

- bob 不能正常查看 alice 的候选人管理能力。
- 页面应提示无权限或返回安全错误。
- 不应泄露候选人操作入口。

### L2 申请状态一致性

目的：

确认同一事件在发布方和申请方看到的状态一致。

步骤：

1. bob 申请 alice 的需求。
2. alice 接受或拒绝。
3. bob 查看“My Applications”。
4. alice 查看收到的申请列表。

预期结果：

- 双方看到的状态一致。
- 不允许一边已通过，另一边仍待处理。

### L3 单人/多人选择模式差异

目的：

确认单人需求和多人需求的选择逻辑不同。

步骤：

1. 创建单人需求，选择 bob 后再尝试选择 iris。
2. 创建多人需求，选择 bob 和 iris。

预期结果：

- 单人需求最终只能保留一个选中人。
- 多人需求可以保留多个选中人。
- 单人需求未选中的待处理申请会结束为未通过。

### L4 Agent 草稿选择逻辑

目的：

确认多草稿场景不会误发布全部。

步骤：

1. 上传可生成两个需求方向的文件。
2. 只选择第一张草稿卡片。
3. 点击确认发布。
4. 到“我的需求”检查新增需求数量。

预期结果：

- 只新增被选中的需求。
- 未选中草稿仍保留或被清晰移除，但不能被发布。

### L5 Agent 意图判断逻辑

目的：

确认“找现有需求”和“我要发布需求”不会混淆。

测试话术：

- `我想打算法比赛，帮我找现有的组队需求。`
- `我想发布一个算法比赛组队需求。`
- `帮我看看有没有人需要前端队友。`
- `帮我发一个找前端队友的需求。`

预期结果：

- “找现有”“有没有需求”应进入推荐已有需求。
- “发布”“帮我发”应进入需求草稿和发布流程。

### L6 API 设置生效逻辑

目的：

确认设置页保存后，不需要重启后端也能影响新的 AI 请求。

步骤：

1. 在设置页保存一个新 API Key。
2. 不重启后端。
3. 立即打开 Agent 发起一条新请求。

预期结果：

- 新请求使用最新设置。
- 至少不能因为旧配置缓存导致直接失败。

## 6. 异常测试场景

### E1 空输入与超短输入

步骤：

1. 在 Agent 输入框直接发送空内容。
2. 输入：`帮我`。
3. 在发布需求页只填标题不填描述并提交。

预期结果：

- 空输入应被阻止或提示。
- 超短输入应触发追问。
- 必填项缺失时有表单提示，不应提交 500。

### E2 重复点击

步骤：

1. Agent 生成需求草稿后，快速连续点击确认发布。
2. 发布需求页提交按钮快速点击多次。
3. 申请加入按钮快速点击多次。

预期结果：

- 不应生成重复需求。
- 不应生成重复申请。
- 按钮应有 loading 或后端幂等保护。

### E3 文件上传异常

步骤：

1. 上传一个空文件。
2. 上传一个非文档文件，例如图片或随机后缀文件。
3. 上传一个较大的文件。

预期结果：

- 页面给出明确提示。
- Agent 面板不会一直 loading。
- 不影响后续继续聊天。

### E4 后端临时不可用

谨慎执行：

- 这个测试不要在正式演示前最后 10 分钟做。
- 只在开发自测时做。

步骤：

1. 停止后端服务。
2. 刷新前端页面或发起请求。
3. 观察错误提示。
4. 重启后端。
5. 刷新页面恢复。

预期结果：

- 前端能提示请求失败。
- 页面不应白屏。
- 后端恢复后刷新可继续使用。

### E5 AI 服务不可达或返回失败

步骤：

1. 在设置页填入无效 API Key。
2. 打开 Agent 发消息。
3. 打开需求 AI 生成或润色。

预期结果：

- 页面不能卡死。
- 应出现错误提示或 fallback 内容。
